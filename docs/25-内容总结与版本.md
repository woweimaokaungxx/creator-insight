# 25 · 内容总结与版本

> **AI 总结**的版本化存储契约（为什么入库、怎么存、重跑为什么不能覆盖），
> 以及**逐字稿正文**的读取与存量回填。
> 关联：`docs/22-任务与状态契约.md`（状态机与不变量的写法）、`docs/adr/0001-异步任务持久化.md`

---

## 一、问题：总结只写文件、不入库

在本版本之前，AI 总结（`summarize` 环节的产出）**只落在一个 Markdown 文件里**：

```
data/transcripts/{视频标题}_AI总结.md     ← 只有这里
data/transcripts/{视频标题}_简体校对版.md  ← 同批产出的另一个文件
```

而同一个响应里的其它产出**都入库了**：

| AI 产出 | 此前去向 |
|---------|---------|
| 简体校对版逐字稿 | ✅ `transcript.text_full_simplified` **+** md 文件 |
| **AI 总结（summary + key_points）** | ❌ **只有 md 文件** |
| 观点 claims | ✅ `claim` 表 |
| 预测 predictions | ✅ `prediction` 表 |
| 时间解析结果 | ✅ `prediction.time_window` / `due_at` |

`ingest_pipeline` 只在事件日志里记了「有没有总结」（`{"summary": true}`），**正文本身没有入库**。

### 由此产生的三个问题

1. **前端无法展示**：视频库/预测页都读接口，接口不返回总结 → 总结等于对用户不可见
2. **语义检索索引不到**：检索只索引库内文本，没入库的内容搜不出来
3. **删文件即丢失**：`data/transcripts/` 被清理或换机器，总结就没了（且无从重新拼装）

---

## 二、决策：单独建表 + 版本化

在「给 `content` 表加两列」与「单独建 `content_summary` 表」之间，选择**单独建表**。

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| `content.summary` + `content.key_points_json` | 改动最小、连表查询方便 | **重跑即覆盖**，无法保留旧版；换模型/换提示词后无法对比；与「内容表只存客观元数据」的职责混淆 | ❌ |
| **单独 `content_summary` 表（版本化）** | 重跑生成新版本、旧版保留；可记录模型/提示词指纹，支持多模型对比；职责清晰 | 需多一次查询、需维护「当前版本」标记 | ✅ 采用 |

理由：总结是**AI 生成产物**，天然带有「模型 + 提示词 + 参数」的上下文。换用 MiMo、换用本地模型、或调整提示词后重跑，产出会不同 —— 直接覆盖会让「哪个版本的总结更好」这个判断**永久失去依据**。这与参考项目 `douyin-creator-distill` 的「**重跑不覆盖，新报告即新版本**」原则一致。

## 三、表结构

```sql
CREATE TABLE IF NOT EXISTS content_summary (
  id              TEXT PRIMARY KEY,
  content_id      TEXT NOT NULL REFERENCES content(id),
  version         INTEGER NOT NULL,          -- 同一视频内递增，从 1 开始
  summary         TEXT NOT NULL,
  key_points_json TEXT,                      -- JSON 数组
  word_count      INTEGER,
  provider        TEXT,                      -- cloud / local
  model           TEXT,                      -- 生成所用模型（多模型对比用）
  prompt_hash     TEXT,                      -- 提示词指纹（换提示词后可对比）
  task_id         TEXT,                      -- 来源 ingest 任务（可追溯）
  is_current      INTEGER NOT NULL DEFAULT 1,-- 1=当前生效；同一视频仅一条
  created_at      INTEGER NOT NULL,
  UNIQUE(content_id, version)
);
```

索引：`content_id`、`(content_id, is_current)`。

## 四、不变式

沿用 `docs/22` 的可判定写法，以下规则由 `app/services/summary_store.py` 强制：

| # | 不变式 | 实现方式 |
|---|--------|---------|
| 1 | **重跑不覆盖**：写入新版本，不 `UPDATE` 旧版正文 | 只 `INSERT` 新行；旧行仅把 `is_current` 置 0 |
| 2 | **当前版本唯一**：同一视频至多一条 `is_current=1` | 先 `UPDATE ... SET is_current=0 WHERE content_id=?`，再 `INSERT ... is_current=1`，两者同事务 |
| 3 | **版本号连续递增**：从 1 开始，+1 递增 | `SELECT COALESCE(MAX(version),0)+1`，并用模块锁串行化「读 max + 写」 |
| 4 | **空总结不写**：正文为空不落库 | 归一化后 `summary` 为空直接返回 `None`，**不占用版本号**（避免版本序列出现空洞） |
| 5 | **版本号按视频独立**：视频 A 的 v3 与视频 B 的 v3 无关 | `UNIQUE(content_id, version)` 而非全局序列 |
| 6 | **事务边界由调用方掌握**：可复用外部连接 | `save_summary(..., conn=...)` 时不 `commit`/`close` |

> 不变式 6 是**硬性要求**，不是可选优化：SQLite 同一时刻只允许一个写者。
> `ingest_pipeline` 在段 3 持有写事务，若本模块另开连接写会立刻 `database is locked`。

## 五、写入路径

`app/services/pipeline.py` 的**段 3**（短事务）内写入，与 claims / predictions 同批提交：

```
段1（短）creator / content / transcript → commit（立即释放写锁）
段2（长）AI 调用：简体校对 → 总结 → 观点抽取 → 预测抽取（不持事务）
段3（短）summary 落库 → claims 落库 → predictions 落库 → commit
```

```python
if summary:
    summary_record = summary_store.save_summary(
        content_id, summary, conn=conn,                              # ← 复用段3 事务
        provider=(summary.get("provider") if isinstance(summary, dict) else None),
        prompt_hash=summary_store.prompt_fingerprint(SUMMARIZE_SYSTEM),
        task_id=task_id, now=now,
    )
```

- `provider` 来自 `ai_gateway.chat()` 的返回（实际走了 `cloud` 还是 `local`）
- `model` 由 `resolve_model(provider)` 按当前配置解析
- `prompt_hash` 用 `prompt_fingerprint(SUMMARIZE_SYSTEM)` 生成（sha1 前 12 位）
- `task_id` 由 `_process_one_video(task_id=...)` 透传

**md 文件仍然照常写出**，两者并存：文件便于人工翻阅与备份，库内记录供接口与检索消费。

## 六、读取接口

| 接口 | 说明 |
|------|------|
| `GET /api/contents/{content_id}/summary` | 当前生效版本；无总结返回 `{"summary": null}`（**不视为错误**，老视频可能尚未生成） |
| `GET /api/contents/{content_id}/summary/versions` | 全部版本（新→旧），供多模型 / 多提示词对比 |
| `GET /api/contents/{content_id}/transcript` | **逐字稿正文**（简体校对版优先、回退原稿），见 §七 |

列表接口 `/api/contents` **不返回总结与逐字稿正文**（避免大文本撑大列表响应），前端点开时按需拉取。

## 七、前端：内容阅读视图

视频库（`src/pages/Library.vue`）每张卡片右下角有「**阅读**」按钮，弹窗内用两个标签切换：

### 7.1 标签一：AI 总结

| 展示项 | 说明 |
|--------|------|
| 版本徽标 `vN` | 当前生效版本 |
| 模型 / 生成时间 / 字数 | 来自 `content_summary` 对应字段 |
| 总结正文 | 独立滚动区（`max-height: 52vh`），长文不撑破弹窗 |
| 要点列表 | `key_points` |
| 历史版本（N） | 多于一个版本时出现，**点击切换**对照查看；当前版本带绿色「当前」标记 |
| 复制正文 | 一键复制总结正文 |

### 7.2 标签二：简体校对版逐字稿

逐字稿正文来自 `transcript.text_full_simplified`（见 §八），展示：

| 展示项 | 说明 |
|--------|------|
| 稿件类型徽标 | `AI 简体校对版` / `原始逐字稿（未校对）` |
| 字数 | `char_count` |
| 来源 | `Whisper 本地转写` / `平台字幕` |
| 正文 | 独立滚动区（`max-height: 58vh`） |
| 复制全文 | 一键复制整篇逐字稿 |

**懒加载**：打开弹窗只拉总结（轻）；**切到该标签时才拉逐字稿**（可能上万字），且同一视频只拉一次。

**为什么逐字稿不版本化**：它是**转写的原始材料**（一条视频一份），不是 AI 生成产物；重跑转写会覆盖旧稿（属于重做而非"新版本"）。这与总结的版本化策略刻意不同。

## 八、逐字稿读取

实现：`app/services/transcript_store.py` 的 `get_transcript()`。

**此前的缺口**：简体校对版早已入库（`transcript.text_full_simplified`），并同时写了一份文件（`data/transcripts/{标题}_简体校对版.md`），但**没有任何接口暴露** —— 用户只能去翻文件，前端读不到。

**回退规则**（判定依据是**简体版是否有内容**，而非字段是否存在，因为早期记录可能为 `NULL` 或空串）：

| 情况 | `text` | `text_kind` | `has_simplified` |
|------|--------|-------------|------------------|
| 有简体版 | 简体校对版全文 | `simplified` | `true` |
| 简体版为 `NULL` / 空串 | 原始逐字稿（可能繁体 / 含识别错字） | `raw` | `false` |
| 无 `transcript` 记录 | `null` | — | — |

前端据 `text_kind` 显示不同徽标，**避免把繁体原稿误当校对稿**。

## 九、存量数据回填

### 9.1 总结：`scripts/backfill_summaries.py`

本版本之前处理的视频**没有** `content_summary` 记录（当时总结只写文件、未入库）。页面上「重新处理该视频」可以补，但对已有 7 份历史 md 而言太浪费（要重跑一遍 AI）。

因此提供一次性回填脚本，直接解析历史文件入库：

```bash
python scripts/backfill_summaries.py              # 预演（只报告，不写库）
python scripts/backfill_summaries.py --apply      # 实际写入
python scripts/backfill_summaries.py --apply --force   # 已有总结的也补一版
```

| 设计点 | 说明 |
|--------|------|
| **匹配方式** | 文件 base（去掉 `_AI总结.md`）与 `_safe_filename(content.title)` **完全一致** —— 写出文件时用的是同一个函数，故可精确匹配，无需模糊匹配 |
| **幂等** | 默认跳过已有总结的视频；`--force` 走版本化写入，**不覆盖**旧版本 |
| **解析结构** | `## AI 总结` 段落 → `summary`；`## 要点` 下的 `- x` → `key_points` |
| **无法恢复的字段** | `word_count` 按正文实际字数兜底；`model` 留空（文件里没有）；用 `provider="file-backfill"` + `prompt_hash="file-backfill"` **标明来源**，便于日后与新生成版本区分 |
| **安全** | 默认预演模式；未匹配到视频的文件只跳过、不猜测 |

### 9.2 逐字稿：无需回填

`transcript.text_full_simplified` 一直是入库的，只是缺接口 —— 本版本补上接口即可读到，不需要数据迁移。

### 9.3 页面空态

- **无总结**：显示「暂无 AI 总结」，提示重新处理即可补上
- **无逐字稿**：显示「暂无逐字稿」（该视频可能只抓了目录、尚未处理）

两者都不报错、不留脏数据。

## 十一、后续可扩展

- **重新总结入口**：给老视频批量补总结，或在页面上「重新生成」（会自然产生 `v2`，不覆盖 `v1`）
- **语义检索索引总结**：目前索引的是逐字稿与预测，可将 `is_current` 的总结一并纳入
- **版本对比视图**：并排 diff 两个版本的总结
- **模型效果评估**：以「总结被人工采纳/引用」为信号反推哪个模型与提示词更好
