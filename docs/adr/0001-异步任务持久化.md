## 一、背景

长视频转写 + AI 抽取耗时可达十几分钟，同步接口必然超时，因此 V0.5 引入了异步 ingest 任务：提交即返回 `task_id`，后台线程处理，前端轮询进度。

当前实现（`app/main.py`）：

```python
_INGEST_TASKS: dict[str, dict] = {}      # app/main.py:145
_INGEST_TASKS_LOCK = threading.Lock()
```

任务状态**只存在于进程内存**，带来的四个问题：

| # | 问题 | 后果 |
|---|------|------|
| 1 | 服务重启后任务状态全部丢失 | 前端轮询 404；用户只能重新提交，**重复消耗 AI 额度与平台请求** |
| 2 | 失败即终止，无重试与错误分类 | 网络抖动导致的临时失败也需人工重跑整批 |
| 3 | 无单条粒度断点 | 批量处理第 N 条失败，前 N-1 条成果虽已入库，但任务层无法表达"部分完成" |
| 4 | 无历史记录 | 用户看不到历史任务、失败原因与产物路径 |

同时，项目已有 `crawl_task` 表（`app/db.py:200`）作为"任务落库"的先例，但它同样只跑一次、无重试、无恢复。

`docs/22` 已定义契约（身份、状态机、不变量），`docs/23` 已定义恢复与重试规则；**本 ADR 解决的是"存到哪里"的决策问题**。

---

## 二、决策

**采纳方案 B：把 ingest 任务迁移到本地 SQLite（三张表）**，并保持 `GET /api/tasks/{id}` 的返回结构向后兼容。

新增表（草案见 `docs/22` §9）：

- `ingest_task`：任务（批次）
- `ingest_task_item`：批次内单条视频明细（单作品状态载体）
- `ingest_attempt`：每次尝试的策略、错误分类与产物路径

---

## 三、备选方案

### 方案 A：保持内存 + 定期 JSON 快照

- 做法：沿用内存 dict，另起线程每 N 秒把 `_INGEST_TASKS` 序列化到 `data/ingest_tasks.json`；启动时加载。
- 优点：改动最小，约 50 行代码。
- 缺点：
  1. **并发写有丢数据风险**（快照间隔内的状态变更会丢）；
  2. 无查询能力——"列出失败条目""统计失败数"都要全量加载 JSON 在内存过滤；
  3. 与 `crawl_task` / `prediction` 等既有表的查询能力割裂，前端要维护两套取数逻辑；
  4. 文件会随任务累积无限增长，需另写清理策略。
- 结论：**低成本但只是把问题推迟**，不解决查询与一致性。

### 方案 B：迁移到本地 SQLite（采纳）

- 做法：建三张表，改造 `_new_ingest_task()` / `_update_ingest_task()` / `get_ingest_task()` 为落库读写（对外函数签名保持兼容）。
- 优点：
  1. **与项目定位一致**——单用户、本地优先、已有 SQLite（`docs/03` / `docs/12` 已明确不引入外部中间件）；
  2. 无新增依赖，复用现有 `get_conn()` 连接与 `_ensure_column()` 迁移工具；
  3. 天然支持聚合查询（失败计数、历史任务列表、口径统一）；
  4. 与 `crawl_task` 的语义可统一，未来可合并为同一套任务语义；
  5. 为"重启断点恢复"提供必要条件（内存态根本无法恢复）。
- 缺点：
  1. 需要三张表与一次数据迁移（无历史数据，实际为零成本）；
  2. 每次状态更新增加一次 DB 写（本地 SQLite + WAL，开销可忽略）；
  3. 需注意 `_INGEST_TASKS_LOCK` 的并发语义要转换为 DB 事务。

### 方案 C：引入外部队列（Redis / Celery / RQ）

- 做法：任务投递到 Redis，worker 消费。
- 优点：支持多 worker 并发、重试机制开箱即用。
- 缺点：
  1. **严重违反项目定位**——单用户本地工具，引入 Redis 意味着用户要多装一个服务并常驻（`docs/12` 明确"不引入额外 worker"）；
  2. 部署复杂度与故障面显著上升（用户机器上 Redis 挂了，产品直接不可用）；
  3. 本项目并发压力极小（单用户串行处理），队列能力完全过剩。
- 结论：**明确不采纳**。

## 四、后果

### 4.1 正面

- 服务重启后任务可恢复（`running → queued`），不再重复消耗 AI 额度；
- 失败可分类、可重试、可查历史，用户能看到失败原因；
- 批次可表达"部分成功"（`partial`），重试只针对失败条目；
- 统计口径统一到 DB，前端不再依赖内存最近 N 条。

### 4.2 负面 / 成本

- **改动面**：`app/main.py` 的任务管理函数（约 §142-190 与 §270-360）、`app/db.py` 建表；
- **兼容性**：`GET /api/tasks/{id}` 与 `GET /api/tasks` 的返回字段必须保持兼容（前端 `useIngestTasks.ts` 已在用），新增字段只增不改；
- **线程与事务**：现有 `threading.Thread` + `_INGEST_TASKS_LOCK` 需改为"线程内写库"，注意 SQLite 并发写（项目已用 WAL + busy_timeout，可承受）；
- **不能解决**的问题：持久化不等于自动重试成功——`needs_action` 类失败（登录失效/验证码/限流）仍需人工介入，这是设计使然（见 `docs/23` §7）。

### 4.3 中性

- 任务表会随使用增长，但量级极低（单用户），暂不需要清理策略；若需要，可参照 `docs/14` 风险 #18（本地文件定期清理）。

## 五、未采纳方案的原因（速查）

| 方案 | 未采纳原因 |
|------|-----------|
| A 内存 + JSON 快照 | 无查询能力、并发丢数据、与既有表割裂，只是推迟问题 |
| C 外部队列 | 违反"单用户本地优先、不引入额外常驻服务"的产品定位，能力过剩 |

## 六、遗留问题

1. **`crawl_task` 是否合并**：关注监控的 `crawl_task` 与新的 `ingest_task` 语义相近，是否统一为一张任务表，留待编码时评估（本 ADR 不预决）。
2. **尝试记录的清理策略**：`ingest_attempt` 会随重试增长，是否需要保留期（如 30 天），后续按实际数据量决定。
3. **多进程/多 worker 场景**：当前为单进程 uvicorn + 后台线程；若未来启用多 worker，需增加任务领取锁，本 ADR 不覆盖。
4. **恢复时机**：启动恢复在 FastAPI `startup` 事件中执行，需确认与现有 `_backfill_content_stats()` 等启动任务的先后顺序。
