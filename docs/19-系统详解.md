# creator-insight · 完整工作流程与功能详解

> 博主观点 → 预测抽取 → 事实验证 → 可信度追踪
> 版本 v0.6.0 ｜ 更新：2026-08-30

---

## 零、系统总览

```
核心定位：自动追踪博主（抖音/B站）在视频里做出的预测，到期后收集证据验证对错，
         长期统计出"谁靠谱、在哪个领域靠谱"。

技术形态：本地 Web 应用（FastAPI 后端 + Vue 前端 + SQLite 存储）
代码规模：35 个 Python 文件 / 约 7000 行 ｜ 42 个 API 端点 ｜ 7 个前端页面
AI 依赖：DeepSeek 官方 API（云端主）+ Ollama（本地兜底）
测试：131 项全绿
```

### 数据链路（8 层）

```
Creator（博主）
  → Content（视频内容）
  → Transcript（转写文本）
  → Claim（观点/断言）
  → Prediction（可验证预测）★核心
  → Evidence（证据，带时间戳）
  → Verification（验证判定，人工锁定）
  → Reliability（可信度统计）
```

## 一、完整工作流程

### 阶段 1：采集（粘贴链接 → 视频元数据）

**触发**：用户在首页粘贴抖音分享文案或 B 站链接

**处理步骤**：

| 步骤 | 说明 |
|------|------|
| 1. 平台识别 | 自动判断抖音/B站，支持分享文案、短链、长链、BV号多种格式 |
| 2. Cookie 准备 | 三级策略（见下） |
| 3. 元数据抓取 | 抖音 detail API / B站 view API；失败时 yt-dlp 兜底 |
| 4. 头像提取 | 顺带取作者头像 URL（抖音 `author.avatar_thumb`、B站 `owner.face`） |
| 5. 入库 | creator / content 写入数据库 |

**Cookie 三级策略**（抖音专用，应对风控）：

```
优先级1 → config.json 的 monitor.douyin_cookie（手动配置，最稳）
优先级2 → data/cookies/douyin_{视频ID}.txt（上次缓存，10分钟内复用）
优先级3 → Playwright 驱动系统 Chrome/Edge 现场生成（自动兜底）
          ├ 访问 douyin.com 主页 → 等 6 秒让 JS SDK 生成 ttwid
          ├ 访问视频页 → 等 12 秒加载数据
          └ 导出约 40 个 cookie
```

实测：完整走自动兜底约 27 秒，可成功获取标题/作者/头像。

### 阶段 2：转写（视频 → 文字）

| 方式 | 优先级 | 说明 |
|------|--------|------|
| 平台原生字幕 | 1 | B站 CC 字幕（需 cookie）、抖音字幕 |
| Whisper 本地转写 | 2 | faster-whisper，模型 `small`，CPU int8，语言自动检测 |
| 简体校对 | 后处理 | AI 将转写结果转为简体中文（避免繁体/错别字） |

---

### 阶段 3：AI 抽取（文字 → 结构化）★ 核心

**四个 AI 任务**（DeepSeek 官方 API）：

#### 3.1 总结（summarize）
输出视频摘要 + 关键要点。

#### 3.2 Claim 抽取（extract_claim）
抽取博主表达的观点、判断、主张。**无法验证的留在 Claim**（如"科创50弹性最大"这类主观分析）。

#### 3.3 预测抽取（extract_prediction）★ 项目灵魂
**不是摘录原话，而是判断博主的预测意图**。三段式分析：

```
第一步：意图判断
  这句话是在【预言未来】，还是在【评论/告诫/回顾】？
  → 告诫("别幻想...")、历史回顾、反讽句 → 不抽取
  → 确实在预言 → 进入第二步

第二步：要素提取 + 推断补全
  subject（标的）：明说
  direction（方向）：明说优先；缺失时从隐含表达推断
      "还有空间/看好/值得布局/性价比高" → up
      "有压力/要回调/别追高/见顶"     → down
      "震荡/磨底/横盘"                 → flat/range
  magnitude（幅度）：只有博主给了数字才填，绝不编造
  time（时间）：没说就标 is_fuzzy，不猜日期

第三步：把握量化
  intent_confidence：AI 对"这确实是预测"的把握（0-1）
  inference_notes：说明哪些是推断的、依据是什么
```

**输出字段**：

| 字段 | 含义 |
|------|------|
| `raw_text` | 博主原话（保持原文，不改写） |
| `interpreted_intent` | **AI 理解的"博主想预测什么"** ← 与 raw_text 的区别所在 |
| `direction_source` | `explicit`（明说）/ `inferred`（AI 推断） |
| `intent_confidence` | AI 对"这是预测"的把握 |
| `inference_notes` | 推断依据说明 |

**后处理规则**：
- 命中告诫/否定词 → 丢弃（无预测意图）
- 完全不可验证（无方向+无幅度+无时间）→ 丢弃
- **时间模糊（"长期会涨"）→ 保留，标 `is_fuzzy` + 待人工** ← 不做一刀切丢弃
- `direction=inferred` 或 `intent_confidence<0.7` 或时间模糊 → 标 `needs_human_confirmation`

#### 3.4 时间解析（parse_time）
将"未来30天""明年"解析为绝对时间戳；无法确定则标 fuzzy，不猜。

**意图推断实测效果**：

| 博主原话 | 结果 |
|---------|------|
| "黄金未来30天会涨超10%" | up（explicit）把握 0.95 |
| "A股明年可能突破4500点" | up（explicit）把握 0.85 |
| "科创50弹性最大"（无方向词） | **up（inferred）把握 0.7** ← 推断生效 |
| "黄金还有空间，值得关注" | up（inferred）标待人工 |
| "别指望房地产大涨" | 正确排除（告诫句） |
| "回顾去年美债" | 正确排除（历史回顾） |

### 阶段 4：人工确认（pending_review → active）

新预测默认 `pending_review`，需人工确认：

```
确认 active  → 必须填 due_at（到期时间）→ 进入 active
确认 invalid → 判定为"不是有效预测" → 归档
```

**设计原则**：时间不确定的预测 `due_at` 留空，等人工填写（系统不猜日期）。

---

### 阶段 5：到期扫描（Scheduler）

```
后台循环（默认 3600 秒一次，可配置）
  → 扫描 status='active' 且 due_at <= now() 的预测
  → 标记为 due（等待验证）
也可手动触发：POST /api/scheduler/run
```

---

### 阶段 6：证据收集（Evidence）★ 防"事后诸葛亮"

**核心设计：Baseline 快照 + 时间隔离**

```
① Baseline（入库时自动生成）
   记录预测发表时点的声明快照，作为时间隔离锚点
   relation='baseline'

② 证据来源（多种）
   ├─ Tavily 搜索：正/反两面查询（需 API key，当前未配置）
   ├─ yfinance 行情：股票/指数/商品的结构化价格数据
   ├─ 人工证据：用户手动添加（带 URL + 发布时间）
   └─ AI 生成证据：无外部搜索时，AI 凭公开知识生成（credibility=0.4，标"未核实"）

③ 时间隔离（最关键）
   post_time_evidence      = published_at >= prediction_at  ← 只有这些能用于判定
   prediction_time_evidence = published_at <= prediction_at ← 仅作背景，不影响判定
```

**为什么这样设计**：防止用"结果发生后才出现的信息"去评价预测（事后诸葛亮）。

---

### 阶段 7：AI 初判（Verification）

```
输入：预测 + 预测后证据 + 预测前背景
  ↓
AI 判定（只用预测后证据）
  ↓
输出 5 种 verdict：
  correct（正确，1.0）/ partial（部分正确，0.5）/ incorrect（错误，0.0）
  inconclusive（无法判定）/ invalid（无效预测）
  ↓
状态 → human_review（等人工复核）
```

AI 需输出推理链：`post_time_facts`（引用的证据ID）+ `judgment`（判断理由）+ `uncertainty_reasons`。

**实测案例**：黄金预测"30天涨10%"，证据显示涨了 8% → AI 判 **partial**（方向对但幅度未达阈值）。

---

### 阶段 8：人工复核 + 可信度统计

```
人工复核（5 种 verdict 任选）
  ↓
写入 final_verdict + locked=1（锁定不可改）
  ↓
预测状态 → final
  ↓
自动重算创作者可信度：
  ├─ base_accuracy（基础正确率）
  ├─ accuracy_by_subject（按标的类型）
  ├─ accuracy_by_domain / horizon / confidence_band
  └─ 样本量门槛（<30 条不显示可信结论）
```

**人工优先原则**：AI 判定只是"初判"，`final_verdict` 以人工为准，锁定后不可修改。

## 五、当前状态与问题

### 5.1 数据健康度

```
内容 65 → 转写 5 → Claim 106 → 预测 21 → 证据 21 → 验证 0
```

| 指标 | 数值 | 评价 |
|------|------|------|
| 预测抽取量 | 21 条 | ✅ 意图推断改造后从 3 增至 21，效果显著 |
| 转写完成率 | 5/65（7.7%） | ⚠️ 大量内容卡在转写 |
| **验证完成数** | **0** | 🔴 **核心闭环未被真实数据验证** |
| 创作者头像 | 1/7 | ⚠️ 历史数据未补齐 |

### 5.2 已知问题（按优先级）

| 优先级 | 问题 | 说明 |
|--------|------|------|
| 🔴 P0 | **验证闭环 0 条** | 产品核心价值（判断博主准不准）从未被真实数据证明 |
| 🔴 P0 | 转写完成率 7.7% | 60 条内容无转写，需失败原因记录 + 重试 |
| 🟡 P1 | 内容主题偏离 | 65 条里财经相关仅少数，大量餐饮/火箭/AI 特效内容 |
| 🟡 P1 | 预测重复 | 同一句话多次入库（测试数据导致） |
| 🟡 P1 | Obsidian 未启用 | 代码就绪但未配置 vault 路径 |
| 🟢 P2 | Tavily 未配置 | 新闻搜索未启用，靠人工/AI 生成证据 |

### 5.3 设计上的限制（非 bug）

| 限制 | 原因 |
|------|------|
| AI 生成证据只对历史预测有效 | AI 知识有截止日期，近期预测诚实返回 inconclusive（不编造） |
| due_at 常为空 | 设计如此——系统不猜日期，等人工确认 |
| 硬预测自动过未开 | 需 30+ 已验证预测才该启用 |

## 七、技术要点与踩坑记录

### 7.1 网络层

| 问题 | 解决 |
|------|------|
| NVIDIA NIM 频繁 504/断连 | 换 DeepSeek 官方 API（快 40 倍） |
| 系统代理长连接断开（127.0.0.1:7890） | 直连优先 + 代理兜底双通道 |
| `extra_body` 参数位置错误 | HTTP 直连时 `chat_template_kwargs` 须放顶层 |
| 抖音/B站 API 风控 | Playwright 自动生成 cookie |

### 7.2 数据库

| 问题 | 解决 |
|------|------|
| AI 调用期间 SQLite 锁死 | pipeline 拆三段（写→AI→写），加 busy_timeout |
| 新增字段破坏老库 | 统一用 `_ensure_column` 做轻量迁移 |
| INSERT 占位符数不匹配 | 改 SQL 后须核对 `?` 数量 = 列数 |

### 7.3 AI 输出

| 问题 | 解决 |
|------|------|
| AI 返回 null 被 Schema 拒 | `symbol`/`unit`/`is_relative` 允许 None 兜底 |
| AI 只用原话不做理解 | 提示词改为意图推断三段式 |
| 模糊表述被一刀切丢弃 | 改为标 fuzzy + 待人工，不丢弃 |

### 7.4 工程

| 问题 | 解决 |
|------|------|
| 旧进程占端口导致新代码 404 | netstat 找 PID → Stop-Process 再重启 |
| 静态目录挂载需重启生效 | 改 main.py 后必须重启服务 |
| vite build 清空目录被安全机制拦截 | `npx vite build --emptyOutDir false` |
| Whisper 强制 zh 导致英文空转写 | `language=None` 自动检测 |
