# 23 · 任务恢复与重试矩阵

> 对标参考项目 `douyin-creator-distill` 的 `docs/任务恢复与重试矩阵.md`。
> 本文件是 `docs/22-任务与状态契约.md` 的**执行细则**：规定各类失败发生时，系统自动做什么、最多做几次、是否需要人工介入。
>
> **文档状态：契约已落地（V0.13，2026-09-13）。**
> 落地前：`app/main.py` 的任务流程在任意异常时直接置 `error` 终止，无重试、无恢复。
> 落地后：错误三分类、单条失败不中断批次、待处理过滤、暂停/继续、重启断点恢复均已实现，
> 见 `app/services/task_store.py`；回归测试 `scripts/v08_test.py`。

## 一、错误三分类

所有失败必须归入以下三类之一，并在 `ingest_task_item.error_class` 落库（枚举值即分类名）。

| 分类 | 含义 | 处理原则 | 典型场景 |
|------|------|---------|---------|
| `retryable` | 临时性故障，重试可能成功 | 有限次数自动重试（默认 ≤3） | 网络超时、连接被重置、下载中断、平台临时 5xx |
| `non_retryable` | 确定性失败，重试无意义 | 直接标记失败，**不消耗重试次数** | 链接失效、作品已删除/转私密、目录审核不通过、AI 返回结构非法且已重试过 |
| `needs_action` | 必须人工处理，自动重试有害 | **立即停止**，任务进入 `waiting_for_action` | 登录失效、验证码、403/429 限流、AI 日配额耗尽 |

### 1.1 判定优先级

```text
1) 先判 needs_action  —— 最高优先，防止触发平台风控或快速烧掉额度
2) 再判 non_retryable —— 避免无意义的重复消耗
3) 其余一律 retryable
```

### 1.2 分类落点

分类判定应集中在 adapter 抛出的异常类型与 HTTP 状态码映射上，**不得散落在业务代码各处**。建议约定：

| 信号 | 分类 |
|------|------|
| `TimeoutError` / `ConnectionError` / 5xx | `retryable` |
| HTTP 403、429、平台"登录失效"提示、验证码页面 | `needs_action` |
| HTTP 404、作品不存在、已删除、私密 | `non_retryable` |
| AI 返回 `json` 解析失败（首次） | `retryable` |
| AI 返回解析失败（已达重试上限） | `non_retryable` |
| AI 日配额耗尽（`daily_call_limit` 触发） | `needs_action` |

## 二、场景策略矩阵

| 场景 | 自动动作 | 最大次数 | 是否推进基线 | 用户入口 |
|------|---------|---------|------------|---------|
| 短暂网络错误、超时 | 当前条目 `retryable` 有限重试（退避） | 3 | 否 | 查看实时进度 |
| 单条视频下载失败 | 标记该条失败，**批次继续处理后续条目** | 3 | 否 | 重试失败项 |
| 单条转写失败（Whisper 本地） | 标记该条失败，批次继续 | 3 | 否 | 重试失败项 |
| 单条 AI 抽取失败 | 标记该条失败，批次继续 | 3 | 否 | 重试失败项 |
| 批量任务中某条失败 | 只标记该条为 `failed`，**不中断整批** | 3 | 否 | 批次结束时汇总为 `partial` |
| 服务重启 | 中断的 `running` 明细退回 `queued`，自动续跑 | 不计为业务重试 | 否 | 自动继续 |
| 登录失效 | **立即停止**，任务 → `waiting_for_action` | 0 | 否 | 重新扫码登录后继续 |
| 验证码 / 风控页 | **立即停止**，不重试、不切换通道 | 0 | 否 | 人工处理后继续 |
| HTTP 403 / 429 限流 | **立即停止**自动请求，进入人工处理 | 0 | 否 | 稍后手动重试 |
| AI 日配额耗尽 | 停止调用 AI，任务 → `waiting_for_action` | 0 | 否 | 调整 `ai.daily_call_limit` 或次日继续 |
| 目录审核不通过 | 保留原始数据，**禁止下游处理** | 按抓取 Loop 的恢复策略 | 否 | 查看待复核目录 |
| 批次暂停 | 当前条目处理完后不再取下一条 | 不限 | 否 | 继续剩余条目 |

> **「是否推进基线」列的含义**：指是否推进**关注监控的增量基线**（`subscription.baseline_video_ids_json`）。任何失败场景都**不得**推进基线，否则会漏掉后续新增视频（对齐 `docs/22` 不变量 #6）。

## 三、重试上限与退避

> **状态：已落地**（`task_store.MAX_AUTO_ATTEMPTS` / `RETRY_BACKOFF_SECONDS`，
> 执行层见 `app/main.py` 的 `_process_with_auto_retry`）。
> 测试：`scripts/v08_test.py` §10（策略）与 `scripts/auto_retry_test.py`（执行循环）。

| 项 | 规则 |
|----|------|
| 单条默认上限 | **3 次**（`ingest_task_item.auto_retry_count`，**独立于** `attempt_count`） |
| 计数范围 | 仅统计 `retryable` 的自动重试；`needs_action` 的人工重试与重启恢复**不计入** |
| 退避策略 | 指数退避 **5s → 20s → 60s**，避免密集重试触发平台风控 |
| 重试粒度 | **只重试失败条目**，已 `completed` 的条目绝不重跑（不变量 #3） |
| 超限后 | 该条目置 `failed`，`error_class` 保留最后一次分类；批次整体置 `partial` |

**两个计数字段的分工**（关键设计）：

| 字段 | 含义 | 谁维护 |
|------|------|--------|
| `attempt_count` | 该条目被执行的总次数（成功 / 失败都算） | `_process_with_auto_retry` **单点维护**，调用方不得再 `inc_attempt` |
| `auto_retry_count` | **仅自动重试**次数，用于判断 3 次额度 | 同上；`mark_auto_retry()` 时 +1 |

> 之所以拆成两个字段：重启恢复与用户手动「重试失败项」都是**合理重跑**，不应消耗
> 自动重试额度（否则服务重启若干次后，本可自愈的条目会因额度耗尽而直接判失败）。
> `attempt_count` 保留全量执行次数用于排查。

**无明细 id 的兜底**：单条任务在明细登记失败等情况下可能拿不到 `item_id`，
此时库内没有计数来源。执行层额外维护**进程内计数**并与库内值取大
（`used = max(本地计数, 库内 auto_retry_count)`），避免「额度恒为 0 → 无限重试」。

**与 AI 额度控制的关系**：条目级重试会重复触发 AI 调用，因此重试上限与 `ai.daily_call_limit`（见 `docs/21`）是**双重保护**——前者限制单条放大，后者限制全局日消耗。两者都命中时，`needs_action` 优先（停止而非继续重试）。

## 四、暂停与继续语义

| 操作 | 语义 | 禁止 |
|------|------|------|
| 暂停 | **安全暂停**：当前条目处理完成后不再取下一條；任务 → `pausing` → `paused` | 不得中途强杀正在执行的条目（会产生无产物但状态为 `running` 的脏数据） |
| 继续 | 只处理**剩余**条目（`queued` + `failed`），跳过 `completed` | 不得从头重跑已完成的条目 |
| 取消 | 停止取新条目，剩余保持 `queued` | 不得删除已产出的产物 |

## 五、重启断点恢复语义

```text
服务启动
  -> 扫描 ingest_task_item 中 status='running' 的明细
  -> 全部退回 queued（保留 attempt_count 不变）
  -> 对应 ingest_task 退回 queued
  -> 后台按队列继续执行
```

| 规则 | 说明 |
|------|------|
| 不计业务重试 | 恢复动作不得增加 `attempt_count`（不变量 #10） |
| 幂等 | 重复执行恢复逻辑不改变结果 |
| 已完成的保持完成 | `completed` 条目在重启后仍是 `completed`，不重复处理 |
| 断点粒度 | 以**单条条目**为检查点，而非整批；这是"部分完成可保留"的前提 |

> **现状差距**：当前任务是纯内存 dict，服务重启后所有 `pending` / `running` 任务**直接消失**，前端轮询会得到 404，用户只能重新提交（并重复消耗 AI 额度）。

## 六、失败带入规则

创建新批次（或点击"重试失败项"）时：

```text
可重新进入待处理：历史 failed 条目
默认跳过：completed / queued / running 条目
```

| 必须保留的信息 | 说明 |
|--------------|------|
| 失败原因（`error`） | 供用户判断是否需要人工干预 |
| 错误分类（`error_class`） | 决定是否可自动重试 |
| 尝试次数（`attempt_count`） | 跨批次累计，避免"换个批次无限重试" |
| 最后任务 ID | 便于追溯是哪个批次留下的失败 |

**空集处理**：若过滤后待处理集合为空，接口返回「所选作品均已完成或正在处理中」，**不创建空任务**（对齐 `docs/22` §6）。

## 七、不可绕过原则

以下情况**一律进入 `needs_action`，不得通过"切换通道 / 换接口 / 重试"绕过**：

1. **登录失效**：不伪造 Cookie、不用匿名通道硬试；
2. **验证码 / 风控页**：不尝试自动识别或绕过；
3. **403 / 429 限流**：不切换通道继续请求，等待人工处理；
4. **AI 配额耗尽**：不静默降级为本地模型继续跑（会掩盖成本问题）。

> 该原则与 `docs/14-risk-register.md` 风险 #1「平台反爬 / 登录态失效」呼应：**宁可停住等人工，也不要把账号打到风控**。
>
> 唯一允许的降级是**用户事先选择的**策略（如 ingest 的 `use_whisper` 开关），而不是系统在失败时自作主张切换。

## 八、用户入口

| 能力 | 展示内容 | 对应接口（现有 / 待扩展） |
|------|---------|------------------------|
| 实时进度 | 当前条目、阶段、总体进度 | `GET /api/tasks/{id}`（语义保持兼容） |
| 批次汇总 | 总数 / 成功数 / 失败数 | `GET /api/tasks/{id}` 扩展 `succeeded` / `failed_count` |
| 失败明细 | 每条失败的原因与分类 | 待扩展（`items[]` 增加 `error` / `error_class`） |
| 重试失败项 | 只重排 `failed` 条目 | 待扩展（`POST /api/tasks/{id}/retry-failed`） |
| 继续剩余 | 只处理 `queued` + `failed` | 待扩展（`POST /api/tasks/{id}/resume`） |
| 暂停 | 安全暂停 | 待扩展（`POST /api/tasks/{id}/pause`） |
| 人工处理提示 | 登录失效 / 验证码 / 配额 | 沿用通知中心（`notify_service`）+ 任务 `message` |

> 前端改造范围：`src/pages/Dashboard.vue`（全局任务进度卡）与 `src/composables/useIngestTasks.ts`（轮询与展示），需支持 `partial` / `waiting_for_action` 的视觉区分。
